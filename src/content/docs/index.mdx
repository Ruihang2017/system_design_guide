## How to use this guide

You've spent years getting things to **work** — wiring up services, shipping POCs, proving ideas fast. System design is a different muscle: making things keep working when traffic goes up 100×, when a server dies at 3am, when the table has 4 billion rows, and when three teams need to change the same system without breaking each other.

The guide is organized so you can **"fan out"**: skim this map, then go deep on one module at a time. Every page is self-contained.

## The arc

- **Modules 0–2** — the mindset and vocabulary. Everything else assumes them.
- **Modules 3–10** — the building blocks you assemble in any design.
- **Module 11** — the method: driving a system design problem or interview.
- **Case studies** — fully worked examples, then a bank of practice problems.
- **Study &amp; resources** — a sequenced [study plan](/resources/study-plan/) and [reading list](/resources/reading/).

:::tip[The throughline]
You already know how to make things work. System design is the discipline of making them **keep** working — at scale, through failure, over years, with a team. Every technique here buys one of those properties, usually by trading away another. Learn the trades, not the trivia.
:::
