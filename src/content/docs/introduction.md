You've spent years getting things to **work** — wiring up services, shipping POCs, proving ideas fast. That's a real skill and most engineers are weaker at it than they think. System design is a different muscle: making things keep working when traffic goes up 100×, when a server dies at 3am, when the table has 4 billion rows, and when three teams need to change the same system without breaking each other.

This guide is organized as a set of self-contained **modules**, so you can "fan out": read the whole thing once for the map, then go deep on one module at a time. The last modules are a study plan plus a list of prompts you can bring back to expand any single module into its own deep-dive.

## The arc

- **Modules 0–2** — the mindset and the vocabulary (non-functional requirements, estimation, consistency). Read these first; everything else assumes them.
- **Modules 3–10** — the building blocks (the "Lego bricks" you assemble in any design: networking, databases, caching, messaging, architecture patterns, reliability, observability, specialized components).
- **Module 11** — the method: how to actually drive a system design problem or interview.
- **Case studies** — two fully worked, then a bank of practice problems with "challenge sheets."
- **Study plan** — a sequenced plan and resources.

:::note[A note on honesty]
Nobody holds all of this in their head at once. Senior engineers don't memorize it — they've *internalized the tradeoffs* so they can re-derive the right answer for a given problem. That's the goal. Aim for understanding the *why behind each choice*, not flashcard recall.
:::
